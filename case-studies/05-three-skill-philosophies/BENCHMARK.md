# 三种哲学的局限 + 怎么混合

跟前 4 个 case 比对一个项目"原版 vs 复刻"不同，本 case 的 BENCHMARK 是**三种哲学各自的天花板**——分析每条路怎么打不通，以及怎么混合补足。

## 各自的天花板

### 自产模式（hermes）的天花板

| 局限 | 现象 | 临界点 |
|------|------|--------|
| LLM 自评不可控 | review 时 hallucinate 出错误经验 | 用户多次纠正同一类错时变得明显 |
| 上下文窗口 | 几百条 skill 撑爆 system prompt | 100+ skills |
| 单用户局限 | A 用户写的 skill 对 B 用户没用 | 多租户场景一开就崩 |
| 演化只能"加"不能"减" | 错的经验沉淀下来不容易消 | 用 3 个月后明显 |
| 反思成本 | 每 N 次 tool call 多一次 LLM 调用 | 高频用户成本翻倍 |

**为啥 hermes 自己活得下来**：单用户工具 + 用 curator 周级清理 + 反例清单挡环境性错误。详见 [case 01 的"长期演化"章节](../01-hermes-skill-evolution/ANALYSIS.md#长期演化skill-库怎么不腐烂)。

### 采集模式（zeroclaw）的天花板

| 局限 | 现象 | 临界点 |
|------|------|--------|
| catalog 鸡生蛋 | 早期没东西可采 | 项目刚启动 |
| 评分被 game | 作者刷下载量 / 假评价 | 生态成熟后 |
| 供应链攻击 | 高分 skill 突然被改为恶意 | 任何时候 |
| 隐私泄露 | catalog 调用暴露查询意图 | 用户敏感 |
| 离线场景断裂 | 没网就没新 skill | 内网部署 |

**zeroclaw 现在处于什么状态**：SkillForge 写了但没真接外部 catalog（没看到 GitHub URL 硬编码 / catalog 协议规范）。等于**采集模式的骨架，没接上水管**。

### 策展模式（ironclaw）的天花板

| 局限 | 现象 | 临界点 |
|------|------|--------|
| 长尾覆盖差 | 用户的小众需求没人写 skill | 用户多样化加深 |
| 演进慢 | 新 skill 等 PR review | 急需场景 |
| 作者激励问题 | 写 skill 没回报 | 第一年没人写 |
| 沙盒维护成本 | WASM 工具链 / WIT 接口演化 | 长期维护负担 |
| 装载流程繁琐 | 用户要 search → install → 测试 | 新手体验差 |

**ironclaw 现在处于什么状态**：33 个 bundled skill 是种子，期望社区扩展。WASM 接口已经定义但生态还没真正起来。等于**策展模式的基础设施完整，等待生态填充**。

## 三种哲学的失败模式对照

| 失败模式 | hermes 表现 | zeroclaw 表现 | ironclaw 表现 |
|--------|------------|--------------|--------------|
| skill 完全没用 | 失败安全（不挂载就好）| 同 | 同 |
| skill 写错（误导）| ⚠️ 影响明显，需手动改 | ⚠️ 评分扛 | ⚠️ 人审扛（理论上）|
| skill 被恶意改 | 不存在（自己写）| ❌ 没拦 | ✅ WASM 边界拦 |
| 上下文撑爆 | ❌ 100+ skills 后 | ✅ 采集模式按需装 | ✅ 同样按需装 |
| 用户骂"不让我自定义"| 不会（agent 自定义）| 不会 | ❌ 想要的没人写 |
| 用户骂"我没装的功能 agent 突然有了"| 不会 | ❌ 自动装可能被嫌烦 | 不会（必须手动）|

每个 ❌ 都是这种模式的**结构性问题**——光修工程细节修不掉，要换模式才行。

## 混合策略 1：A + C 组合（隐私优先 + 选用商业 skill）

**场景**：单用户工具但允许选择性引入第三方功能。

```
默认: 模式 A (自产) 全开
用户主动: skill_install <商业 skill> → 模式 C (装到沙盒)
```

例子：本地 Claude Code 风格的助手。日常用法靠 hermes 模式累积偏好；要装"GitHub PR 自动评论"这种功能时走商业 skill 装到 WASM。

**好处**：隐私保护 + 选择性扩展
**代价**：用户要懂两套体系（自产 skill vs 装的 skill）

## 混合策略 2：B + C 组合（生态丰富 + 严格审计）

**场景**：企业 / 团队产品，希望快速生长但底线要稳。

```
默认安装: 模式 C (审核过的核心 skill)
用户可选启用: 模式 B (允许 agent 从 catalog 采集, 但仍走沙盒装载)
```

例子：企业级 agent 平台。核心功能由公司审核的 skill 提供；用户可勾选"允许 agent 自动从社区 catalog 找补充 skill"，被采集的 skill 进沙盒。

**好处**：长尾 + 安全双保
**代价**：评分模型 + 沙盒接口都要做，工程量大

## 混合策略 3：A + B + C 三件套（完整生态）

**场景**：要做大的 agent 平台，覆盖所有用户层级。

```
新手用户:        模式 C (装精选 skill)
高级用户启用:    模式 A (本地 skill 演化)
平台后台:        模式 B (扫 catalog 发现新值得策展的 skill)
                    ↓
              人工审核后转入模式 C
```

**好处**：覆盖全频段（从小白到极客 + 平台主动建设）
**代价**：三套机制都要维护，团队大才扛得动

## 推荐路径（按团队规模 / 阶段）

| 阶段 | 推荐 |
|------|------|
| 个人工具 / 1-3 人团队 | **纯 A** (hermes 路线)，跟用户跑就行 |
| 早期创业 (10-30 人) | **A + 简单 B**（A 做主，跑 catalog 自动化补长尾）|
| 增长期 SaaS (50+ 人) | **B + C**（生态做起来，安全边界守住）|
| 成熟平台 (200+ 人) | **A + B + C**（高级用户给 A，普通用户给 B+C）|

## 一句话总结

**hermes、zeroclaw、ironclaw 不是竞争关系，是 agent skill 生态在不同发展阶段的三种快照**。

- hermes 是**起点**——一个用户一份 skill 库，从无到有
- zeroclaw 是**中段**——开始有公开 catalog，agent 学会自己找
- ironclaw 是**成熟态**——多方贡献者 + 严格安全边界 + 商业化可能

要做一个长期可活的 agent 产品，**最好的设计是允许这三种哲学共存**，按用户阶段 / 信任级别切换。
