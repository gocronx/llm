# 三种 Skill 哲学 —— 抽出来的设计模式

跟前 4 个 case 抽具体机制不同，本 case 抽出来的是**架构层的选型决策**。三个模式各自适合不同的产品形态。

## 模式 A · 自产模式（Self-Produce）

```
对话 → 后台 LLM 复盘 → 写 markdown → 下次装载
```

**核心做法**：agent 在每次有意义的会话后，**自己反思自己**，把经验沉淀成 markdown。下次会话开始前装回 system prompt。

**核心组件**：
1. Review 触发器（计数器 + 阈值）
2. Review prompt（"Be ACTIVE" 之类的偏置语 + 反例清单）
3. skill 写入 API（agent 能调）
4. 装载机制（启动时拼 prompt）
5. 清理机制（curator agent / 时间归档）

**适用产品**：
- ✅ 单用户工具，长期跟随同一用户
- ✅ 用户偏好稳定但难表达（格式 / 流程）
- ✅ 部署在用户本机，隐私敏感
- ✅ 团队规模小（一两个核心维护者）

**不适用**：
- ❌ 多租户 SaaS（每用户独立 skill，互不可见）
- ❌ 要严格审计的合规场景（LLM 自评质量不可控）
- ❌ 一次性 agent / 比赛 / demo（自产没机会用）

**主要风险**：
- skill 质量飘（LLM 自评 ≠ 人审）
- skill 污染（环境性问题被误记成永久规则）
- 上下文撑爆（积到几百条要做主题分桶 + 召回）

## 模式 B · 采集模式（Forage）

```
catalog 扫候选 → 评分 → 自动安装 → 装载
```

**核心做法**：把 skill 当**外部资源**，agent 像爬虫一样从公开 catalog 扒，按评分自动筛。

**核心组件**：
1. Catalog scanner（GitHub / npm / 自家中心化仓库）
2. Scoring model（来源信誉 / 用户评价 / 安全审计）
3. Auto-installer（高于阈值的自动装）
4. Refresh schedule（定期回扫，catalog 在变）

**适用产品**：
- ✅ 公开生态 / 开源产品，能利用社区贡献
- ✅ 需要覆盖**长尾需求**（不可能自己写完所有 skill）
- ✅ 用户接受"agent 替我做决策"
- ✅ 有信任的中心化 catalog 可以依赖

**不适用**：
- ❌ 内网 / 离线环境（无 catalog 可访问）
- ❌ 隐私 / 合规敏感（catalog 调用可能泄露查询意图）
- ❌ catalog 还没起来（鸡生蛋问题，最初没东西可采）

**主要风险**：
- 评分被 game（作者刷数据）
- 供应链攻击（恶意 skill 通过评分）
- catalog 下线导致整个能力降级

## 模式 C · 策展模式（Curated）

```
作者写 → 仓库审 → 用户安装 → 沙盒装载
```

**核心做法**：skill 是**人审过的产品**，agent 只是个搬运工。装载时走沙盒（WASM / Docker）防作者作恶。

**核心组件**：
1. 中心化 catalog（带审核流程）
2. Skill 元数据 schema（版本 / 签名 / 依赖 / 权限申请）
3. 安装工具（agent 能 search / install / remove）
4. **沙盒**（关键，因为信任作者 ≠ 信任作者今天没被入侵）
5. 权限模型（每个 skill 申请它需要的 capability）

**适用产品**：
- ✅ 企业 / 商业产品，质量要求高
- ✅ 多用户共享 skill（同一份给所有人用）
- ✅ 跨用户调试性强（出问题能复现）
- ✅ 有人专门维护 catalog（公司 / 社区核心团队）

**不适用**：
- ❌ 个人工具（策展开销不值）
- ❌ 高度个性化需求（每用户偏好不同 → 策展覆盖不到）
- ❌ 快速迭代产品（人审太慢）

**主要风险**：
- 长尾覆盖差（没人写就没有）
- 演进慢（PR review 周期）
- 作者激励问题（谁来写）

## 三模式混合策略

最强的产品**混用三种**，按场景路由：

```
用户请求 → 命中已装 skill?
            ├─ Yes → 用 (任一模式都装载过的)
            └─ No  → 查 catalog (模式 B)
                     ├─ 有高分匹配 → 自动安装 (模式 B)
                     ├─ 有候选但分低 → 提示用户决策 (模式 C)
                     └─ 无 → 后台复盘当前会话生成新 skill (模式 A)
                              ↓
                         可选: 用户允许的话, 提交回 catalog (反向贡献模式 B/C)
```

**zeroclaw 是离这个目标最近的**（SkillForge 已经做了 B，SkillImprover 写了 A 但没接，没有 WASM 沙盒做 C）。

**hermes 是 A 的纯粹版**（不参与 B/C 生态）。

**ironclaw 是 C 的纯粹版**（不要 A，把 B 视为低质量来源排除）。

## 几个常被忽略的决策因子

### 信任模型决定一切

| 信任谁 | 选哪个 |
|------|-------|
| agent 跟自己 | 自产 (A) |
| 公开数据 + 评分 | 采集 (B) |
| 人审 + 签名 | 策展 (C) |

**别赌反了**——如果你信不过 LLM 自评（合规场景），别走 A。如果你认为 evaluate 函数能挡 99% 恶意（创业初期 SaaS），可以走 B。

### 谁来当 catalog 主人

- 模式 A：不需要
- 模式 B：需要一个能扫的源（公开 GitHub 也算）
- 模式 C：需要一个有 SLA 承诺的中心化仓库

如果你没人维护 catalog，**别选 C**。ironclaw 不缺人，所以能走 C。

### 长尾 vs 头部

- 模式 A 覆盖**单用户的长尾**（每个用户都有特殊偏好）
- 模式 B 覆盖**跨用户的长尾**（很多人都需要但小众）
- 模式 C 覆盖**跨用户的头部**（大家都需要的核心能力）

三者维度正交，不冲突。

### 演进速度需求

- 模式 A: T+0（这一轮聊完就能生效）
- 模式 B: T+小时（catalog 扫一次的周期）
- 模式 C: T+天/周（PR review + 发布周期）

要"今天发现问题今天修"必走 A 或 B。

## 反例：哪些组合不要做

- ❌ **纯采集没本地审计**：catalog 被攻陷直接全完
- ❌ **纯自产没 curator**：6 个月后变垃圾堆（hermes 自己也加了 curator）
- ❌ **策展不带沙盒**：失去策展的核心价值（人审挡不住作者明天的代码漏洞）
- ❌ **三模式同时给一个 skill 多份**：哪份生效？冲突解决变噩梦
- ❌ **采集模式下 agent 自动安装但不告诉用户**：用户看到 skill 列表多了一堆陌生东西会失控
