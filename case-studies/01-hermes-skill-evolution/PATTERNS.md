# 抽出来的设计模式

把 hermes-agent 的"越用越聪明"剥到只剩骨架，是这么个模式：

## 核心模式：Post-turn Reflection Loop

```
┌─────────────────────────────────────────────┐
│ 主对话回合 = 用户感知到的"对话"               │
│   user → agent[读 skill 索引] → 回答         │
└──────────────────┬──────────────────────────┘
                   │ (回答已发出)
                   ▼
        ┌─────────────────────┐
        │ 异步：复盘 LLM 调用  │
        │  - 读完整 transcript │
        │  - 决定是否产 skill  │
        │  - 写 markdown 到盘  │
        └─────────────────────┘
                   │
                   ▼
        下次启动 → 装载 skill → system prompt
```

四个不可省的组件：

1. **触发器**：按啥触发？hermes 用"工具调用次数 ≥ 10"。也可以是回合数、token 数、用户显式 `/save-lesson` 命令。
2. **反思 prompt**：决定后台 LLM 用什么口径产 skill。**最关键的设计点**：要不要 "Be ACTIVE" 偏置 / 要明确哪些事别记。
3. **持久化格式**：markdown 文件 + 文件系统。不是数据库不是向量库。文件可以肉眼看、git diff、手工编辑。
4. **装载机制**：下次启动怎么进 prompt。是塞索引还是塞全文，要不要按主题筛。

四个都得到位才闭环。少任何一个都不"越用越聪明"。

## 这模式什么时候值得抄

✅ **强烈推荐**：
- 用户对你的 agent 有**稳定的偏好模式**（格式、流程、用词），同一种纠正会反复来。把它沉淀成 skill，每次会话避免重复纠正。
- agent 跑**重复领域的任务**（写代码、查日志、跑 SQL），存在可复用的"操作手册"。
- 你的产品有**长生命周期用户**（不是一次性 demo）。
- 你愿意接受**异步学习**（这一轮的 lesson 要下一轮才生效）。

⚠️ **可以抄但要改**：
- 多用户场景。hermes 是单用户假设。多用户得给 skill 加 namespace（`user_id/skill_name/SKILL.md`），还要考虑 skill 跨用户共享（基础 skill）vs 私有（偏好）。
- token 紧的场景。一次塞几百个 skill 索引到 system prompt 真的会撑爆。要按主题分桶 + 按需召回。

❌ **别抄**：
- **一次性 agent** / **demo / 比赛 / 临时脚本**。学了也用不上几次，纯浪费。
- **强幻觉敏感**领域（医疗、法律）。后台 LLM 写 skill 会引入新的幻觉源 —— 它可能误总结一条错的"经验"，下次拿来当真。
- **用户期望"忘记"**的场景。一旦写盘默认就持久了。隐私 / 合规要先想清楚怎么删 / 怎么过期。
- **任务高度差异化** 的 agent。skill 是 "this class of task" 才有价值，每次任务都不一样的话，写出来的 skill 全是单次噪音。

## 实践要点

### Prompt 偏置怎么设

hermes 的 "Be ACTIVE" 是高 recall 的选择：宁可错记一条，不漏掉一条。
反面是 "高 precision"：除非有强信号，不要产 skill。

选哪头看**用户耐心**：
- 用户能接受 skill 多了之后慢慢手动清理 → 偏 recall
- 用户不会管 skill 库的清洁 → 偏 precision，免得垃圾堆积

hermes 还在 prompt 里明确列了**反例**（环境问题、临时报错、否定性结论不要记），这个清单比"积极"那句话还重要。没有反例清单，"积极"会让 LLM 把 "browser tool 启动失败" 这种环境性 bug 永远刻进 skill，几个月后 bug 早修了它还在引用。**反例清单是高 recall 模式的安全网**。

### 持久化格式：为什么选 markdown 而不是 JSON / 数据库

- **可读** —— 用户能自己开文件编辑器看 / 改
- **可 diff** —— 进 git 自然就有审计
- **可被 LLM 直接消化** —— 不需要 schema 解析，直接拼进 prompt
- **可手工修** —— 模型写错了，人能纠正

代价：没有强 schema，写歪了得靠 prompt 收敛。

### 装载经济学：索引 vs 全文

hermes 选择 **索引模式**（只装 name + description，按需读全文）。
计算：100 个 skill × 平均 50 字描述 = 5K 字索引（约 7K token）。可控。
如果全文塞，100 个 × 平均 800 字 SKILL.md = 80K 字。爆。

实现要点：**索引必须包含足够的判别信息**（description 要写清楚"什么时候用我"），否则 LLM 不会去 `skill_view` 读全文。

### 触发器：选啥维度

| 维度 | 优点 | 缺点 |
|------|------|------|
| tool_call 数（hermes 选） | 跟 agent 工作量正相关 | 简单对话学不到东西 |
| user message 数 | 简单 | 跟实际复杂度脱钩 |
| token 数 | 跟成本对齐 | 阈值难调 |
| 用户显式触发（/save-lesson） | 信号最强 | 用户懒得用 |
| LLM 自评判（每回合问"该记吗"） | 灵活 | 多一倍 LLM 调用 |

实践：用 tool_call 阈值做默认，用户显式触发做兜底。

### 双层 cache 的工程价值

`mtime + size` 做指纹 → 进程重启不重扫。
看起来是工程细节，**但是它决定了 skill 库能不能扩到几百条**。没缓存，启动延迟跟 skill 数线性增长，用户 3 个月后就会嫌慢。

抄这个模式时不能省。

## 抄这模式必须想清楚：第二个机制——清洁工

只做"写"不做"清"的 skill 系统跑半年就崩。ANALYSIS.md 的"长期演化"那一节剖了 hermes 怎么治这个 —— 这里抽出**抄的时候必须做哪些 / 可以省哪些**。

### 必抄（硬机制）—— 没这些半年后用户骂街

| 机制 | 工作量 | 不做的代价 |
|------|-------|----------|
| **usage 追踪 sidecar** | 半天（一个 JSON 文件 + atomic write） | 完全没法判断哪些 skill 该清，所有后续机制无米下锅 |
| **stale → archive 时间阈值** | 半天（一个定时任务 + config 阈值） | skill 库无限膨胀直到把 system prompt 撑爆 |
| **归档不删（.archive/ + restore）** | 1 小时（就是 mv 而已） | 误清了找不回来 → 用户彻底不信任系统，反而手工保留所有 skill |
| **pin 机制** | 1 小时（usage.json 加个字段） | 长尾但关键的 skill 被自动清掉，再也想不起来曾经有过 |
| **CLI 兜底（prune / status / restore）** | 1 天 | 用户没法看清自己的 skill 库，更没法干预 |

5 项加起来 ≈ 3 天工程量。**这是不抄就崩的下限**。

### 选抄（软机制）—— 决定上限有多高

| 机制 | 工作量 | 收益 |
|------|-------|------|
| **独立 curator agent（周级）** | 3-5 天（独立调度 + 专用 prompt） | skill 库自己会"重构"，前缀簇被合并，narrow skill 降级为 references |
| **class-level 命名约束**（hard） | 1 天（建命名 blacklist + reject） | 比 hermes 强 —— hermes 全靠 prompt，烂名字常溜过 |
| **embedding 相似度去重** | 2-3 天（每次 create 前算一遍） | 比 hermes 强 —— hermes 完全靠 curator LLM 肉眼 |
| **skill 命中率统计** | 半天（每次 view / use 记一笔，按月输出 top/bottom） | 用户看得到自己的 skill 库到底有没有用，决定后续投入 |

软机制都是"能让 hermes 不漏的事被代码堵住"的 —— **如果你团队没人能持续调 curator 的 prompt，软机制反而比 hermes 抄过来更可靠**。

### 反例：哪些不要抄

- ❌ **每写一个 skill 都立刻全库相似度去重**。计算量大、噪音多、容易把新加的 skill 误判为重复。hermes 选周级 curator 是对的。
- ❌ **自动删除（不归档）**。无论你多自信都不要直接 `rm`。用户找不回来一次就彻底不信任。
- ❌ **没 dry-run 的批量操作**。`curator prune --days 60` 必须有 `--dry-run`。LLM 决策不透明，每次必须先让用户看清要动哪些。

### 一个简单优先级

如果只有 5 天预算：
1. 必抄 5 项（3 天）
2. 简单的统计 + 命中率（半天）
3. 命名 blacklist + 拒绝（1 天）
4. 剩下半天写 CLI

curator agent 和 embedding 去重留到下一版。先有"能扛半年"的下限，再追"越用越精炼"的上限。
